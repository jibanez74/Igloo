# Library scanning and artwork

This reference covers catalog discovery, enrichment, file reconciliation, the library watcher, and managed artwork. [FFmpeg and playback](ffmpeg.md) owns probing outputs and playback behavior; [OpenAPI](openapi.json) owns scan/settings endpoint schemas. Provider behavior here describes Igloo's implementation, not a promise about external catalogs.

Each scanner admits one run at a time, captures its configured root, and participates in shutdown cancellation. Configured libraries scan at startup; with the watcher enabled, its catch-up walks replace those startup scans. Saving a library path alone does not launch a scan unless the watcher is enabled. Admin scan endpoints start asynchronous work and expose the current/latest in-memory report, not persistent history. See the [watcher](#library-watcher) for queued requests during a run of changes.

## Movie enrichment

Implementation: [movie scanner](../server/cmd/internal/scanner/movie), [TMDB ranking](../server/cmd/internal/tmdb), and [retry backoff](../server/cmd/internal/scanner/backoff.go). Local technical work is committed before optional provider enrichment.

Movie technical updates and TMDB enrichment are separate. New and changed files are probed and commit file-derived duration/runtime, streams, chapters, and fingerprints transactionally. TMDB failures or unavailability preserve existing descriptive fields and relationships; new movies use filename-derived defaults. Confirmed enrichment replaces TMDB descriptions and relationships atomically, including manually edited descriptions, while retaining audience rating and file-derived duration/runtime. Movies with a TMDB identity fetch details directly by that ID; only movies without an identity use filename search. Failed ID lookups never trigger rematching.

Internal `movie_tmdb_retries` rows cascade with their movies. Later startup or manual scans retry eligible unchanged movies with pending enrichment or no TMDB ID, without probing again when their filesystem baseline is unchanged. Each movie gets at most one enrichment attempt per scan. Request failures and unavailable TMDB stay eligible for the next scan; a no-match result is subject to the miss backoff described under [file-change detection](#file-change-detection). Successful enrichment or manual Identify clears the retry in the same transaction. These metadata-only retries preserve technical metadata and [playback caches](ffmpeg.md#probed-metadata-and-cache-invalidation). Completion logs report enrichment successes and outstanding pending enrichment.

TMDB requests run outside the scanner database mutex. The short persistence transaction rechecks the catalog ID, stored path, observed TMDB identity, pending state, and file baseline. Deleted or replaced catalog rows discard in-flight work; a manual Identify that changes the identity discards stale enrichment while allowing valid technical updates to the surviving row. Identify shares the scanner write mutex and preserves audience rating and file-derived duration/runtime. Cancellation, unstable files, and transaction failures publish no partial metadata, fingerprints, or cache changes within each transaction. Technical work committed before an interrupted enrichment stays available. Enrichment runs only inside scans; there is no background retry worker or forced refresh.

The shared [TMDB ranking](../server/cmd/internal/scanner/tmdbmatch/match.go) retains title-similarity signals with bounded release-year weights (`+20` exact, `+12` adjacent, `−15` other known mismatches) and a combined popularity/vote contribution capped at `13`. Sequel bonuses require a sequel marker in the target title. A single ambiguous, non-parenthesized year token triggers both parsed title/year and full normalized title searches; explicit parenthesized release years keep their interpretation. Candidates merge by TMDB ID, retain their strongest score across interpretations, and break ties deterministically by title then ID. A failed search does not discard candidates from another successful search; cancellation stops resolution. The highest-ranked candidate is enriched whenever its details are available, regardless of confidence, without low-confidence warnings. The manual picker uses the same ranking.

## TV show scanning

The TV scanner (`server/cmd/internal/scanner/show`) runs at startup and through admin `POST /api/settings/scan/shows`, using the `shows_dir` captured when starting. `SHOWS_DIR` seeds this setting on first launch. Saving library settings does not launch scans, except that with the library watcher on, a library whose path changed is armed again and walked once. The scanner shares the launcher and start guard, shutdown context and wait group, 60-second quiet period, metadata-only fingerprints, worker pool, transaction runner, progress reporting, and safe reconciliation used by the movie scanner: the whole library is discovered first, two workers parse, inspect, and probe files, and the scan goroutine alone persists each result. Unlike movies, TV has no in-run retry window: a deferred file waits for the next scan, and a failed probe is reported as a failure without the post-probe filesystem revalidation movies apply.

In the web client, Settings → Libraries provides a TV Shows **Scan Library** button once its directory is saved. Saving normally only persists the path in SQLite and scanning is a separate action; with the library watcher on, changing the path also walks the library once. The button is disabled while the TV path has unsaved changes, a settings save is pending, any library's scan request is pending, a TV scan is running, or the TV scan status is still loading or failed to load. Feedback confirms asynchronous scan startup or displays the server error, including an already-running scan. Progress is reported below the control from `GET /api/settings/scan/shows`, which is admin-only and serves the current or latest in-memory run: state, phase, file counts, local episode count, entity enrichment counts, and up to 100 outstanding issues. There is no persistent scan history.

Discovery accepts `Show Name (optional year)/Season N/file`, `Show Name/Season N - Title/file`, `Show Name/SN/file`, `Show Name/Specials/file`, and episode files directly inside the show folder, where the token alone names the season (`S00Exx` files are specials). A season directory must agree with the token. Case-insensitive `S01E02`, inclusive `S01E02-E04`, enumerated `S01E02E03`, and `1x02` tokens are accepted. Numeric episode titles are accepted after a hyphen surrounded by whitespace (including repeated spaces or tabs), such as `S02E09 - 4 Days Out` or `1x02 - 1984`; attached numeric extensions such as `S01E01-03` remain invalid. Standalone resolution tokens with 3–4 digits on each side of an unspaced `x` (case-insensitive), such as `1920x1080` or `[1280X720]`, are ignored before counting episode tokens. They require non-alphanumeric boundaries or filename edges, may appear before or after numbering, and never establish an episode by themselves. Multiple genuine episode tokens remain conflicting even alongside resolution metadata. Specials use season zero. Conflicting or malformed numbering, reversed ranges, and filename/directory season mismatches are logged and rejected. Absolute-number and date-based numbering are not inferred. Hidden entries (including backup directories) and nested extras are excluded. NFO files and external subtitle sidecars are ignored. Video extensions and file/directory symlink behavior match movies.

Cleaned absolute show-directory paths identify shows; separate folders never merge by TMDB ID. Seasons and logical episodes exist only for successfully probed files. A combined file links multiple episodes in filename order; duplicate copies link the same logical episode. Each new or changed physical file is probed once using the shared [technical metadata rules](ffmpeg.md#probed-metadata-and-cache-invalidation). Its technical rows and fingerprint belong to the file. File duration is never divided into guessed episode runtimes or start offsets. Episode runtime is TMDB metadata only. File updates retain the file ID and commit local fallbacks, technical rows, links, and enrichment markers atomically; changed filesystem metadata re-probes the file instead of hashing it.

After technical processing and safe cleanup, eligible pending enrichment runs sequentially in show/season groups; the entity total is published before the first request. TV search uses the folder title and optional premiere year with unfiltered fallback, the shared title ranking and ambiguous-year interpretations, deterministic ties, and no confidence cutoff. Each show lookup and each season fetch has a 30-second budget. A definitive no-match is reported as unmatched rather than failed, records a miss, and skips the show's seasons and episodes; repeated misses back off from one day up to seven before the show is searched again. Stored show IDs are fetched directly and never automatically rematched. Show details include aggregate credits, content ratings, external IDs, and videos; season details supply aggregate credits, videos, and episode descriptions together with each episode's guest stars and crew, so no per-episode request is made. Missing episodes remain pending. Successful show/season credits preserve every character and job; episode guest cast and crew are stored per episode, while regular cast lives in the show and season aggregate credits. US certification is preferred with a nonempty-country fallback; metadata defaults to English. Remote artwork paths and trailer metadata are stored without thumbnails; while `download_images` is on, the show, season, episode, network and people images follow the [artwork rules](#library-artwork).

Each entity's required responses must succeed before its metadata and relationships replace prior values transactionally. Requests run outside the database mutex; persistence rechecks the show path and all owning IDs, numbers, and observed TMDB identities. Failed show lookups defer descendants while other shows continue. Each entity is attempted at most once per scan; a season response is reused for its local episodes, and a failed season response fails every entity that depended on it. Success clears retries; failures and unavailable TMDB retain them for later scans. An authentication failure, or three consecutive transient provider failures, stops enrichment for the rest of the run with one scan-wide issue. Metadata-only retries do not probe or rebuild technical rows. Successful unchanged entities are skipped. A technical file change never re-queues a matched show, season, or episode; only entities without a TMDB identity are queued, so descriptive metadata is never rewritten by a rescan. TV response caches use separate keys and are cleared with other TMDB caches.

Cleanup follows the [root-identity and confirmed-nonexistence checks](#missing-file-cleanup). File deletion cascades through links and technical rows; the same transaction prunes the file's season of episodes with no files, then that season if it has no files, then its show if it has no seasons. A re-processed file prunes only its season's episodes that no longer have files. Removing one copy preserves episodes with other copies. Shared people, genres, companies, networks, and extra videos remain. Observed failures and deferred files are protected. A file renamed or moved within its season keeps its row, and a renamed show folder keeps its show; see [missing-file cleanup](#missing-file-cleanup). Completion logs and the status report distinguish imported, updated, unchanged, deferred, failed, and deleted files from local episode and entity enrichment counts (updated, failed, unmatched, and pending): one file can carry several episodes, so the two never add up. TMDB season/episode totals are stored separately from available counts derived from file relationships.

Scanned shows are read back by the show details endpoints, which serve a read-only page of seasons, episodes, and credits and describe no media behavior; episode playback is described in the [playback guide](ffmpeg.md#media-identity-and-requests). Manual Identify, alternate/DVD numbering, NFO ingestion, and background metadata refresh are not implemented for TV; the [library watcher](#library-watcher) covers TV like the other libraries.

After a TV file transaction commits, `InvalidateCommittedShowFile` receives the file ID and affected episode IDs under the scanner mutex. On deletion those episode IDs are captured before cascades remove the links. The [playback guide](ffmpeg.md#probed-metadata-and-cache-invalidation) owns the cache effects and limitations.

## Music catalog and provider matching

Implementation: [music scanner](../server/cmd/internal/scanner/music). For new and changed `.m4a` files the scanner also reads the Apple catalog IDs an iTunes Store purchase carries, the track's `cnID` and its album's `plID` in `moov/udta/meta/ilst`, which ffprobe does not expose. It reads them through the descriptor it already holds for fingerprinting and stores them internally, whether or not Apple lookups are on, since unchanged files are not read again. A file whose metadata cannot be read has no IDs and is otherwise processed normally.

Music scans process files sequentially in batches. Each scanner instance admits one scan at a time, captures its configured directory when starting, and tracks the launched goroutine in the shutdown wait group. Cancellation or expiry of the scan context interrupts index loading, walking, probing, metadata resolution, and persistence, including the final partial batch. Interrupted scans do not report successful completion or record cancellation as a provider lookup failure.

Each music track is persisted in one SQLite transaction, including its file fingerprint, musician and album enrichment, provider match bookkeeping, genres, and relationships. Any database failure rolls back the track transaction. Provider lookup failures still permit local-tag fallback. After a successful commit, the scanner invalidates the track's runtime cache while still holding the shared scanner database mutex; once the transaction runner releases it, the scan records the file fingerprint in its scan index and merges the transaction's cache entries. Lookup outcomes and compound-artist splitting decisions last for the scan; database entity IDs use transaction overlays. Relationship writes are idempotent and do not use accumulation caches.

Music identity uses Go's trim-and-lowercase normalization (including Unicode) for artist names, album title plus effective album artist, and music genres. Explicit sort tags never participate in identity. Internal identity tables retain normalized aliases separately from display spelling. A Spotify or Apple Music match that already belongs to another catalog entity retains that owner's ID, atomically moves aliases, track references, credits, and metadata contributions, then removes the duplicate. Track IDs, playlist entries, and listening history remain intact. Entity caches are invalidated after a merge commits. These normalization rules apply to music only; movie identity and movie genres follow their own rules.

Match bookkeeping keeps one outcome per entity: the provider that settled it (`spotify` or `apple`), and the status and reason used by retry and compound-credit reconciliation, plus, for a Spotify miss, the best candidate's name and (when one was scored) its score, so a wrong miss can be explained. Provider IDs remain on the catalog entities; an album holds an Apple ID or a Spotify ID, never both, and musicians are matched on Spotify only. A `failed` outcome also counts the failed lookups in a row and, from the second, the time before which the retry pass skips the entity: one day after the second failure, doubling per further failure up to a week (the TMDB miss backoff). Any other outcome clears both. Duplicate provider IDs and search diagnostics are not stored.

Albums whose files carry an Apple collection ID are matched on Apple Music first when the stored `enable_apple_lookups` setting is on. The setting is read when each scan starts and seeded from `ENABLE_APPLE_LOOKUPS`, which defaults to true. Such an album skips the Spotify album search during the walk unless an outcome already settled it; that holds for its files without an ID too, as long as one of its files has one. After the walk and cleanup, the Apple pass reads its candidates in pages of 100: albums with an ID and no outcome, plus Apple-matched albums with tracks still to pair (files added or changed since). It looks their collections up through the keyless iTunes Lookup API in the US storefront, up to 50 per request with three seconds between requests, asking for up to 200 songs per collection and for each collection at most once per scan. An album's collection is the one most of its files carry, ties going to the lowest ID. When the catalog lists it, the album stores the Apple ID, the 640-pixel artwork as its cover, the track count, and the album type: `single` for a title ending ` - Single` or ` - EP` (the catalog calls every collection an album), `compilation` for "Various Artists", otherwise `album`. Apple writes no dates, genres, titles or artists. Each of the album's tracks without an outcome then pairs exactly by the Apple track ID its file carries, against every listed collection the album's files name, storing the Apple ID and explicit flag; a track no listed collection holds is `unmatched`, with reason `not_listed` when its file has an ID. Songs past a collection's 200th are not returned, so files for them stay unpaired. A collection another album already holds merges the two, as a Spotify collision does. After a merge, pending tracks pair against all collections named by the surviving album's files, including those it already owned. If any of those collections has no cached answer yet, the valid album match and merge still commit, but no pending track receives an outcome. Pairing resumes when later candidate processing or a subsequent scan has answers for every collection; a confirmed unlisted collection is an answer, not a lookup failure. Lookups remain outside persistence transactions and reuse the scan's cached answers. An album whose collection the catalog no longer lists is recorded as `unmatched` with reason `not_listed`, which hands it to Spotify's search in the same scan; Spotify's outcome then replaces it. An incoming album with a collection Apple did not answer for records nothing and waits for a later candidate or scan without a Spotify search. The API takes no credentials, so every Apple failure is transient: three failed requests in a row stop Apple lookups for the rest of the scan, with one scan-wide issue. Two consequences follow from settling an album once: a brand-new album whose first processed file has no Apple ID is searched on Spotify during the walk and keeps that match, and an album Spotify settled while Apple lookups were off is not revisited when they are turned on.

The Spotify enrichment path does not write musician summaries or Spotify genre links; those columns and API fields remain but are not populated by that path. Spotify stopped reporting popularity and follower counts to Development Mode apps in February 2026, so the catalog stores neither. From a matched artist it stores the Spotify ID and the first image as the thumbnail. From a matched album it stores the Spotify ID, the first image as the cover, the album type (`album`, `single` or `compilation`; anything else is stored as unknown), the track count, and the release date as the fallback described below. Album matching sends the album artist's Spotify ID when it is already known, which makes a candidate crediting that ID certain and one crediting a same-named artist doubtful, and lets a release year and track total from the files' tags break ties between editions. A release with fewer than half the tracks the tags count, such as the album's lead single, is marked down. A compound album artist (`A, B & C`, split like track credits) agrees with a candidate crediting any one of its names, and "Various Artists" on either side names no artist, so it scores like a candidate without credits. Album titles are also compared without bracketed or ` - ` qualifiers that mention a remaster (`(OJC Remaster)`, `[2021 Remaster]`), and `Vol.` reads as `Volume`. When an artist's own name search misses but a matched album credits an artist whose name agrees with the local one, the first agreeing credit with a nonempty ID is looked up by ID and adopted, and saved with the track even when the track credits someone else; a compilation credited to "Various Artists" never qualifies.

Each Spotify-matched album's track list is loaded with its details. After the files are processed, the link pass pairs each album's tracks with that list in one step, so each Spotify track goes to one file. Pairings are ranked: the Spotify track at the file's disc and track number with an agreeing title comes first, then a track whose title agrees, then the track at the file's position whose length is within two seconds. The best pairings are taken first. Track titles are also compared without featured-artist, "From …" source and remaster qualifiers (`(feat. X)`, `- Remastered 2011`), and a version word (live, demo, remix, mix, acoustic, instrumental, alternate, take, reprise, finale, unplugged, karaoke) in only one title's bracketed or ` - ` qualifier keeps the titles apart. Only a duplicate file, with the same title and a length within two seconds of the file holding a Spotify track, shares that track. A pairing stores the Spotify track ID and explicit flag on the track and fills in a missing track number, never a disc number or a tagged value. A track that pairs with nothing is recorded as `unmatched` and is final, with reason `track_claimed` when the tracks it would take went to other files. A changed file drops its pairing and is paired afresh the same scan alongside the album's already-paired files, whose tracks stay taken. An album match is dropped when its tracks contradict it. That happens when the album has at least three local tracks, fewer than half of them pair, and either at least one Spotify track is left unpaired or the Spotify release has fewer than three tracks. A bigger local edition holding every track of a Spotify album of three or more keeps its match; a single is not an edition of the album. The album's Spotify ID, cover, type, track count and date are cleared, along with its tracks' pairings and outcomes, and the album is recorded as `unmatched` with reason `tracks_disagree`.

Internal `music_spotify_adoptions` rows retain the target artist ID when adoption fails temporarily or the breaker defers it. Album retries save the matched album and its adoption outcome or pending target in one transaction. A later scan resumes pending adoption by ID even after a final name-search miss, without another name search, album match, or probe. Success and terminal 404 clear the pending row atomically; deleting or merging away the musician cascades its pending row. Cancellation rolls back the interrupted persistence, leaving either the previous pending target or the still-unmatched album eligible for recovery. Each artist ID, including failed lookups, is requested at most once per scan.

Spotify requests stop for the rest of a scan after a fatal failure (rejected credentials or an exhausted quota) or three consecutive transient ones (rate limits, server errors, transport failures); a 404 for one entry is neither. Entities after the stop record no outcome and retry on a later scan, and the run reports one scan-wide issue. A rate limit without the quota reason whose `Retry-After` is at most five seconds, and ends before the request's deadline, is waited out and the request retried, at most twice; any other rate limit goes to the breaker. Requests are not otherwise retried or paced, and the client keeps no cache: the scan context de-duplicates lookups and persisted outcomes cover later scans.

After the filesystem walk, the final track batch and the Apple pass, a Spotify-enabled scan retries catalog artists and albums whose outcome is missing or `failed` and whose failure backoff has elapsed (except albums still waiting for Apple), albums Apple handed over as `not_listed`, and artists with pending adoption. Candidates must be referenced by current tracks; a pending album artist also qualifies through an album alias with tracks, even when those tracks credit someone else. The scan then pairs the tracks of matched albums that still lack an outcome or whose `failed` outcome's backoff has elapsed. Track lists are cached by Spotify album ID, so aliases and merged albums share results, including empty lists. Cached lists remain usable after the breaker opens; failed direct fetches are also attempted at most once per scan. Albums matched this scan pair from the track list their match brought along; any other album's list is fetched once per scan (a 404 settles its pending tracks as unmatched). Pairing from lists already at hand continues after the breaker stops requests. Candidates are read in pages of 100 and resolved sequentially from persisted local metadata without running ffprobe. An entity is looked up at most once per scan, including changed-file attempts; `matched` and confirmed `unmatched` outcomes are retained. Each external request runs outside the scanner database mutex, and each result is persisted in a short transaction. Temporary failures remain eligible for the next scan, then follow the failure backoff. Cancellation interrupts requests and persistence without recording a Spotify failure or reporting completion. Completion logs include matched, failed, and unmatched lookup counts and the number of tracks paired. Spotify being unavailable does not prevent local import.

Original artist tags and explicit per-credit artist sort values are stored internally. Comma suffixes `Jr`, `Sr`, `II`, `III`, and `IV` accept an optional trailing period, while `V` and `Vi` require one; matching ignores case and surrounding whitespace. A suffix stays with the name before it also when ` & ` follows it, so `Leslie Odom, Jr. & Lin-Manuel Miranda` is two credits. Bare `V` and `Vi` are separate credit candidates, subject to the split rules (including keeping ambiguous combined names offline). For compound credits, a retry establishing a split-worthy confirmed non-match reconciles previously imported credits without probing their files. Interrupted credit reconciliation resumes on a later Spotify-enabled scan. Parallel explicit sort credits are associated with ordered artist occurrences, including duplicate artists. Sort parsing retains duplicate values and empty positions. When the number of ` & `-separated values matches the occurrence count, those boundaries take precedence and commas inside inverted names remain intact. Otherwise, the comma/suffix form is accepted only when its count matches. Ambiguous raw sort tags remain stored without assigning guessed per-artist values. File processing and Spotify credit reconciliation share these rules; sort values never decide whether an artist name is split. When duplicate credits or merged identities resolve to one artist, their nonempty values contribute one lexically selected vote per track.

Artist and album sorting use the most common nonempty explicit local sort value across their current tracks, with binary lexical tie-breaking. Generated fallbacks are not votes; removing all explicit values restores the retained display name or album title. Album dates use the most common valid parsed local track date, with ties resolved to the earliest date. Track dates accept ISO dates (`2006-01-02`, or without leading zeros as `2006-1-2`), dates with a time, RFC 3339 timestamps (as iTunes writes them), year-month, year alone, US `MM/DD/YYYY`, and European `DD-MM-YYYY`. A timestamp keeps the calendar date it was written with rather than being converted to UTC, year-month dates are read as the first of the month, and year-only dates as January 1. A tag in any other format is logged at debug level as an unreadable tag and leaves the date empty. Dates, like Apple catalog IDs, are parsed only when a file is imported or changed; unchanged files are not re-read. Spotify album dates are stored separately and used only when no valid local track date remains; the exposed year follows the selected date. Derived updates run only when values change, including after track changes and entity merges. Artist and album enrichment writes, Spotify ID assignments, and changed derived values set `updated_at` to SQLite’s current timestamp. Unchanged derived values and unchanged artist thumbnails or album covers skip their updates and preserve timestamps, although other metadata writes in the same scan can still advance the row timestamp.

Musician–album links derive from current track credits and album membership. Local musician and album genres derive from current track genres and credits; a link disappears only after its last supporting track changes or is deleted. Genre relationships keep a provenance column (`local` or `spotify`), but this enrichment path writes only local genre links; API genre lists return each genre once. SQLite reconciles local relationships on credit, genre, and album changes, including explicit album deletion. Removing and restoring a relationship within one scan works without a stale relationship cache. Otherwise unreferenced artists, albums, and genres are retained.

All three scanners use the shared filesystem walker. It follows file symlinks to inspect the target's type and size, while retaining the symlink path as the catalog identity. Only regular-file targets with an accepted path extension are processed. Broken links with accepted extensions are reported through the walk-error callback; special files are skipped, and directory symlinks are not traversed. Missing-file reconciliation follows the [cleanup rules](#missing-file-cleanup).

## Missing-file cleanup

Startup and manual scans, and the library watcher's catch-ups, capture the configured directory and reconcile missing catalog files after a successful walk and completed local processing, before movie enrichment and the music Apple Music and Spotify passes. Candidates include rows without fingerprints and are restricted by cleaned absolute path containment within that directory. Files observed by the walker are protected before processing, including unchanged, deferred, and failed files. A file observed and then deleted is reconciled on the next scan.

Only `os.Stat` confirming nonexistence permits deletion, including broken symlink targets and files in removed subdirectories. Existing special files, permission and I/O errors, and symlink loops preserve records. Cancellation or fatal walk failure before cleanup skips it. Cancellation or deadline expiry during cleanup keeps committed deletions, rolls back the interrupted transaction without invalidating its caches, and reports scan interruption at Warn level without successful completion or music enrichment. Other cleanup failures are logged as errors. The library root must remain readable with the same filesystem identity, including for empty libraries; root accessibility and identity and file absence are checked again immediately before each deletion commits. Filesystem checks cannot be atomic with a SQLite commit. The library watcher (below) keeps its own mount monitoring so a dropped mount never reaches a run of changes.

A walk the server starts on its own (a startup scan, which is a catch-up, or a watcher catch-up) keeps files that look unmounted rather than deleted, since a filesystem that is not mounted leaves an empty, readable mount point. It keeps every file when its walk finds none while the catalog holds some under the root. Otherwise it keeps the missing files beneath a mount point an earlier run recorded that is not mounted now, such as a disk mounted inside the library that has not come up after a power cut, and reports an issue naming the mount point. Every run that reaches cleanup records the mount points beneath the root that its walk passed through (a mount point beneath which it found a file, or the root), from the kernel's mount table (`/proc/self/mountinfo`; `getfsstat` on macOS), by path rather than device number, since device numbers follow probe order and change across boots. Catch-ups and runs of changes, which may import a newly mounted disk's first files, only add to that record, so a disk still missing stays protected across restarts; a library scan an admin requests deletes every missing file and records only what is mounted then, which is how the files of a disk removed for good go. Filesystems outside the library are not seen: the branches of a pool such as mergerfs, whose pool stays mounted while a branch is missing, and the targets of file symlinks into another mount, as rclone or debrid libraries use, whose broken links read as deleted files.

Each deletion matches the original catalog ID and stored path in a short transaction under the scanner database mutex. Foreign-key cascades and search triggers remove dependent records. Music deletions also recalculate affected artist sorting and album sorting, dates, and year from remaining tracks. Unreferenced shared artists, albums, and genres remain. Runtime caches (including the playback data and room teardown described in the [playback guide](ffmpeg.md#session-lifecycle)) and in-memory fingerprints are invalidated only after commit. Committed deletion totals are reported as the `deleted` field of each scanner's completion log. A file renamed or moved within the library keeps its catalog row, and with it watch progress, likes, playlist entries, watch rooms and its provider match. Before processing, each file the walk found at a path the catalog does not hold is paired with the run's cataloged file of the same inode, size and modification time that the walk did not see at its own path (the device is left out, since device numbers change across reboots; a fingerprint two such rows share pairs neither), and the row is re-keyed to the new path once the old path is confirmed missing, before and again immediately before commit, so a copy or a hard link that leaves the original in place is cataloged on its own. Music pairs each batch before processing it, since it processes during the walk. Processing then checks the file at its new path like any other: a renamed file's new ctime probes it again (music hashes it, and only records the new fingerprint when the bytes are the same), which also catches a tagger that rewrote it in place keeping its size and modification time; a file in a renamed folder keeps its ctime and is unchanged; a file renamed moments before a scan may be deferred until it is quiet, its row already re-keyed. A run's moves count toward `catalog_revision`, so the web client refreshes its lists after a watcher run that only moved files. A renamed unmatched movie's title and year follow the new file name (a move that keeps the name keeps them, edits included), and when it searches differently it is searched on TMDB again at once rather than after its miss backoff, since a rename is how a wrong or missing match is fixed; an untagged track keeps the title its old file name gave it. A renamed show folder keeps its show, seasons and episodes, and takes the new folder's local name and year, once the old folder is gone and the new one has no show; an unmatched show's display name follows, and it is searched again at once. A matched show moves while the new folder name agrees with its match: the same title, and the same year, no year, or an added year its first air date bears out, as Sonarr's `{Series TitleYear}` folders add. Any other rename of a matched show is how a wrong match is fixed, since shows have no Identify, so its files are imported as a new show and searched again, as before, losing its watch progress. An episode file renamed to other episode numbers keeps its row and is linked to them. An episode file moved to another season, a show folder split across two new folders, a file copied rather than moved (a new inode), and a file changed while it moved (a new modification time, as a retag that also renames) are imported anew and their old rows cleaned up. On a mergerfs pool, whose default inode calculation derives from the branch device, a rename made while the server is down may not pair at the next startup, though renames the watcher sees while it runs do; a rename across branches under a path-preserving policy becomes a copy, which does not pair.

## File-change detection

Movie, TV, and music inspection share regular-file, filesystem identity, symlink, quiet-period, and descriptor/path validation. The cleaned catalog path is the lookup key. A successful filesystem baseline contains size, nanosecond modification and status-change times, and device and inode identity. Complete matching filesystem metadata skips probing.

Movie inspection reads **zero content bytes** and stores no checksum. A new file, missing baseline, or changed filesystem metadata requires probing. Identical bytes with changed filesystem metadata (for example, permission changes or replacing a file with a copy) can trigger a reprobe and playback-cache invalidation, because movie scans never prove byte equality. Same-size edits with restored modification times are detected through status-change time on supported platforms.

Music uses full-file SHA-256 hashing, including embedded tags and artwork. Changed metadata triggers sequential full hashing with a reusable 256 KiB buffer and cancellation checks. If size and digest still match, only the fingerprint changes; catalog timestamps, relationships, and playback caches are preserved. Changed bytes are probed and resolved normally, retaining the catalog ID at that path. TV inspection matches movies: no content is read, and changed filesystem metadata re-probes the file while retaining its catalog ID.

Files must be quiet for 60 seconds after the later of modification and status-change time. Future-dated files remain deferred. The detector reports an outcome, observed baseline, deferral reason, and earliest quiet-period eligibility. Descriptors for new or changed files remain open through local processing. Regular-file type, descriptor/path identity, size, timestamps, and symlink resolution are checked when opening, after probing, and immediately before commit. Detected writes, disappearance, replacement, or symlink retargeting defer the file while preserving its previous catalog and baseline. Inspection, probe, and database failures also preserve prior records. Music retries deferred files on a later startup or manual scan.

Movie post-probe filesystem validation also runs after failed probes. Detected file changes take precedence over probe failures and defer the file for retry; when validation succeeds, the original probe failure is retained.

Movie scans first discover eligible files and establish totals, protecting observed paths from cleanup. Two probe workers receive explicit file/baseline inputs through bounded queues; a single coordinator owns scan maps, caches, counters, and persistence. Each accepted movie commits technical metadata, streams, chapters, its baseline, and pending-enrichment state atomically under the shared scanner database mutex, before contacting TMDB. Technical commits apply the [playback invalidation rules](ffmpeg.md#probed-metadata-and-cache-invalidation). New movies are usable with filename-derived descriptions while enrichment is pending.

After initial local processing, deferred movie paths receive at most two retries within a 120-second window, respecting quiet-period eligibility. Unresolved files remain explicitly deferred. Missing-file cleanup follows the conservative rules above. After local processing and cleanup, two enrichment workers resolve pending movies, with serialized descriptive persistence. Each movie receives at most one complete TMDB resolution per scan, limited to 30 seconds including HTTP retries. Three consecutive transient provider failures or an authentication failure stop new enrichment dispatch; up to two active requests can finish. Valid no-match results do not trip this stop condition. A first miss is retried on the next scan; from the second consecutive miss the movie backs off, doubling from one day up to seven days, so unidentifiable files stop costing a lookup per scan. Manual Identify resets the backoff; a technical rescan of the same file keeps it, since the search is derived from the unchanged file name. Successful enrichment and manual Identify clear pending state. Files and catalog identities are revalidated before applying results; descriptive updates do not invalidate playback data.

`GET /api/settings/scan/movies` is admin-only and returns the current/latest in-memory run identity, state, phase, timestamps, active filenames, unique local-file counts, deletion totals, separate enrichment counts, pending enrichment, and up to 100 safe outstanding issue summaries with their full count. States distinguish idle, running, completed, completed-with-issues, canceled, and failed; completed-with-issues means at least one issue is still outstanding when the run ends (an issue is dropped when a later retry of the same file succeeds), while pending enrichment alone (for example movies backing off after misses) leaves a run completed. Retried files count once. There is no persistent scan history. `POST` keeps duplicate-scan protection through discovery, local work, retry waits, cleanup, and enrichment. For administrators, every authenticated route polls each scanner's status: every two seconds while a scan runs, every ten seconds while it is idle and Settings → Libraries is open or while the request keeps failing, and once a minute otherwise, so a run of watcher-detected changes is noticed on any route. Polling runs only while the page is visible. The client keeps cached status across navigation, refreshes statistics as imports commit, and invalidates movie queries at phase transitions and termination; a run of watcher-detected changes (`scope: "changes"`) invalidates them once, when it ends, if `catalog_revision` moved, which a run that only moved files also advances. Phase changes and final outcomes are announced accessibly.

Shutdown cancellation interrupts worker dispatch, probes, TMDB requests, retry waits, and database operations, and joins workers before completing the scan goroutine. Committed work is retained; interrupted scans never report success. Logs include phase transitions, ten-second progress snapshots, inspection/probe, persistence, and enrichment operations taking at least five seconds, individual failures, and final accounting. Detailed paths/errors stay in logs; API issues contain filenames and safe explanations.

Internal `track_file_fingerprints`, `movie_file_fingerprints`, and `show_file_fingerprints` tables cascade with catalog rows. Timestamps are integers and unsigned filesystem identifiers are decimal text; size is stored on the catalog row. Only track fingerprints contain a 32-byte SHA-256 blob. Baselines and transaction cache overlays are published only after successful commits. Hashing, probing, and external requests run outside the shared scanner database mutex. There is no background checksumming, persistent scan history, or duplicate merging; renames and moves within the library are recognized as described under [missing-file cleanup](#missing-file-cleanup).

## Library watcher

With `enable_watcher` on (seeded from `ENABLE_WATCHER` only for a new database), `internal/scanner/watch` follows the movie, show and music roots and applies each change through a *run of changes*: the scanner's normal pipeline limited to the changed paths. When the setting is off nothing runs: no goroutine, inotify instance or timer. The setting and the library roots take effect on save, without a restart; turning it off returns only once every watch is released.

- **Backends.** Linux roots on local filesystems use one inotify instance (stdlib `syscall`) with a watch per directory the scanner walks; shows watch only show and season folders. A directory inside the library that the server cannot read is logged and left unwatched, as the scanner walk skips it, rather than pausing the library or moving it to polling; only an unreadable root pauses it. Roots on NFS, SMB/CIFS, FUSE (mergerfs included), 9p or Ceph, and libraries with such a mount inside them, are polled instead, as is every library on macOS and any library that reaches the `fs.inotify.max_user_watches` limit. The filesystem types come from `/proc/self/mountinfo`, so classifying a library never touches a share. A poll stats each known directory every three minutes and lists only those whose mtime or identity moved, so a NAS can spin down between polls; a directory that could not be listed, such as one without read permission, is listed again on every poll until it can be. In a changed directory it reconsiders every media file, including existing names that may have been atomically replaced; scanner fingerprints skip probing unchanged neighbors. New and reconsidered files are checked every 30 seconds while settling and reported once their complete filesystem metadata, including device and inode, held still across polls and they have been quiet for 60 seconds. A file rewritten in place changes no directory, so in a polled library it is only picked up by a library scan.
- **Batching.** A library's changes dispatch together once it has been event-quiet for 2 seconds, capped at 30 seconds from the first change. A file dispatches once its writer closed it (`IN_CLOSE_WRITE`), it was created by a hardlink or move, or it went untouched for 60 seconds, and 5 seconds have passed since its last mtime or ctime change. A permission or timestamp change (`IN_ATTRIB`) does not count as the writer closing it. Files that are ready wait for others that only need to finish their quiet period, for at most 30 seconds, so an album copied track by track is one run. For inotify, removals wait while another file of the library is still settling, within the cap, and files ready meanwhile wait with them, since one may be a removal's new name. The poller holds removals and completed additions together until all its observed files finish settling, before handing them to this batching stage; the batching deadline cannot release a polled removal early. This keeps both names of a polled rename in one run and preserves the episode's identity and progress. The hold lasts at most 10 minutes from when a removal first waited, so a file that is written continuously cannot hold back the library's deletions for good; a file that cannot be read never settles and goes to the scanner at once, which reports it. A standalone removal with nothing settling is reported immediately, unless a catch-up walk is owed, and outages or re-arming discard held changes in favor of a catch-up walk. Sidecars and temporary names (subtitles, NFO, `.part`, rsync temporaries) are ignored by extension.
- **Runs of changes.** `StartChanges` reads only the catalog rows at or beneath the changed paths, walks only those paths (missing ones visit nothing), and removes only rows under them, through the same confirmed-missing cleanup. Its quiet period is `ChangeQuietPeriod` (5 seconds) instead of 60, which is safe because the watcher waited for the writer and `Validate` still rejects any write that lands during processing. Deferred files are handed back to the watcher instead of waiting through the 120-second movie retry window; in a polled library they go back to the poller, which must see them hold still again under the polling rules above before they dispatch, since the scanner found them changing after the poller had settled them. Music limits its Apple Music and Spotify passes to the albums and artists of the tracks the run touched. A run of changes shares the scanner's one-run launcher, so the watcher never applies anything while a library scan or catch-up runs: it keeps collecting events, its batches are refused and retried every 5 seconds, and what it saw during the scan is applied after it. Each run publishes its own report, but a run of changes also lists the issues the previous run left at paths outside its own, or at or beneath a path it could not read (for files it did not see and that still exist), that stay true until a run looks at them again: files that failed or were deferred, and disks kept because they were not mounted. So a library scan's failed files stay listed through the watcher's runs; carried issues come after the run's own and do not make its state completed-with-issues. Discovery and enrichment issues stay with the run that raised them, since a run of changes may fix them without naming them, as when it enriches a show it touched. A library scan requested during a run of changes is queued behind it (`POST` answers 200 "queued"), and the status reports `scope: "changes"`. Only one library scan waits, and it reads the configured root when it launches, so it walks the root configured then and is dropped if the library was cleared meanwhile. Requests coalesce into it: a watcher catch-up and a queued admin scan become one catch-up, which hands deferred files back to the watcher and, since the admin asked for a library scan, cleans up as one does. Every status also carries `catalog_revision`, a count of the scanner's catalog changes across runs; a music status's count also includes committed Apple Music and Spotify track pairings even when files are unchanged or only their fingerprints changed, and album matches dropped because their tracks contradicted them; several runs of changes can finish between two polls of the status, so the web client refreshes its lists and statistics when the revision moves, not from the counters of the one report it saw.
- **Catch-up walks.** Arming a library (turning the watcher on, server startup with it on, a changed root, the end of an outage, an inotify queue overflow) walks the whole library once. An overflow arms every inotify library again, dropping its pending changes: one may be half of a change whose other half was lost, such as a rename's old name without its new one, which a run of changes would apply as a deletion, along with the episode's progress. Events lost while a library is still being armed arm it again once that walk lands. With the watcher on, these replace the startup scans. With the watcher off, the startup scans are catch-ups too: nothing saw what changed while the server was down. A catch-up keeps the 60-second quiet period, and its cleanup keeps files that look unmounted rather than deleted; see [missing-file cleanup](#missing-file-cleanup). Until an owed catch-up has started, the library's changes wait for it.
- **Symlink targets.** The configured root, including symlinks in its parents, is resolved again during each bounded inotify layout check (every 30 seconds), before each poll, and, for an inotify root that resolves through a symlink, before each run of changes dispatches, since the old target's watches keep reporting changes that the scanner would apply under the new one. A changed target releases the old watches and pending changes, selects the appropriate backend again, and requests a catch-up before applying new changes. A broken target or an inotify resolution check that exceeds the existing 10-second bound pauses dispatch until the root recovers; unchanged targets retain the mount and identity checks below. Late reports from replaced pollers are ignored.
- **Mount loss.** A dropped mount leaves an empty, readable mount point, which a scan would read as a deleted library. The watcher records whether the root is a mount point and every mount beneath it; `IN_UNMOUNT`, the root's removal or move, a root that does not answer within 10 seconds (a hard-mounted share whose server is down), or a polled share answering `EIO`/`ESTALE` pause the library, and nothing is dispatched for it until the root and all of its mounts are mounted again (checked every 30 seconds), when it is armed and walked once. The layout check (every 30 seconds for an inotify library, on each poll for a polled one) also reads the mount table for a filesystem mounted since the library armed on a directory its walk reached, such as a disk that came up late after a power cut: mounting over a watched directory sends no event, so the library is armed again and walked once, which watches what the disk brings. From then on that disk is part of the layout, so unplugging it pauses the library like any missing mount until it is back or the library settings are saved. Mounts the walk never reaches, such as the snapshots ZFS mounts beneath its hidden `.zfs` directory, are ignored. Saving the library settings also re-arms a paused library, for a layout that changed for good. Arming an inotify library records its root and adds a watch to every directory on a goroutine of its own, outside the shutdown wait group like the pollers: a mount inside the library that hangs after the root answered keeps only that library from dispatching, never the other libraries, a settings save or shutdown. Directory events from watches the walk added before the watcher registered them are held and applied once it lands (file events are not: the catch-up that follows covers them, and a copy running during the walk would otherwise fill the buffer), and the watches of a walk that finished after its library was armed again are released once no other walk is in flight, since the kernel shares a watch between walks of the same directory. A walk that outlives its session stops at its next watch, as the closed instance refuses it rather than adding it to whichever instance reused its descriptor.

## Library artwork

With `download_images` on (seeded from `DOWNLOAD_IMAGES` only for a new database), `internal/artwork` keeps a copy of each movie and show poster and backdrop, season poster, episode still, network logo, cast and crew photo, album cover and musician photo in the static directory, and the API returns the copy in place of the TMDB path or the Spotify or Apple URL. Each image column holds the value the API returns, and a `_source` column beside it the provider reference that the scanners and the movie editor write. Triggers in `schema.sql` return a new source at once and keep a copy while the same source is written again. A new provider ID, which names the copy's folder, returns the source too (a show's for its seasons and episodes, an album's Spotify or Apple ID), and a pass points a column at a copy only while the row's ID still names that copy's folder, so no column points into a folder its row has left.

- **Layout.** Copies live under the static directory at `movies/<tmdb_id>/<title>_poster` and `_backdrop`; `shows/<tmdb_id>/<name>_poster` and `_backdrop`, with the show's `season_NN_poster` and `sNNeNN_still` beside them; `networks/<tmdb_id>/<name>_logo`; `people/<tmdb_id>/<name>_profile`; `albums/<spotify_id or apple_id>/<title>_cover`, named by whichever provider matched the album; and `musicians/<spotify_id>/<name>_thumb`. Two files of one movie, or two folders of one show, share a copy; the images of a show without a TMDB match, or of an album or musician without a provider ID, stay remote. When two images of one folder would share a name, as a show named "Season 01" would with its first season, the first listed (movies, people, shows, seasons, episodes, networks, albums, musicians, each by row) keeps it and the other stays remote. The title or name is folded to lowercase ASCII words joined by underscores (`untitled` when nothing is left), and the extension follows the type the downloaded bytes sniff as: JPEG, PNG, GIF or WebP. SVG sources stay remote, since an SVG served from the API's origin can run script. TMDB images are fetched at the sizes the clients show: w500 posters and stills, w1280 backdrops, w185 photos, w92 logos. Album covers and musician photos are fetched at the http or https URL stored, Spotify's largest image or Apple's 640-pixel artwork. The URL is `/api/static/<path>?v=<hash of size and source>`: static files are cached for a year, and a replaced image keeps its name.
- **Passes.** One goroutine runs passes, one at a time; requests made during a pass share one pass after it, a full one if any of them asked for one. A full pass runs at startup, after every library scan and catch-up, after a settings save that changes `download_images` or `static_dir`, and after an Identify or a metadata edit; a watcher run of changes asks for a pass of changes (below). The database records the static directory the copies were made in; a pass in any other directory first points every column back at its source and records the new one, so it downloads every copy there again and overwrites files found there, which may predate a source change, also across restarts. A full pass then lists the catalog, points stale copies (a new source, title or size, or a missing file) back at their source, downloads what is missing with four workers outside the scanner mutex, and points the columns at the copies in short transactions under it. A column whose source changed during the download keeps the new source, and each transaction first checks that the setting is still on in the same directory, so a pass never points a column at a copy after a settings save pointed them back. Finally it removes the files in the managed folders that no column points at, and the folders left empty. Writes leave `updated_at` alone, since movie playback fingerprints include it.
- **Passes of changes.** A pass after a watcher run of changes reads only the image columns that still return their source (new rows and sources, and images that failed or stay remote), through partial indexes on those columns, so it reads no table whole. It then fixes the key folders those images belong in and lists every row with an image in them, in the order a full pass lists them, and in those folders alone it reuses, names, downloads and removes exactly as a full pass does. It reads no other folder or file, so copies of deleted rows, copies under an old title or size, copies deleted by hand and the copy a row left behind in the folder of its old provider ID wait for the next full pass, unless the pass works in that folder, where nothing points at them any more. A copy missing from a folder it works in is downloaded again, even when every copy it lists is missing: the unmounted-disk check of a pass of changes is the one under "Safety". A pass of changes runs as a full pass in a static directory other than the recorded one, once a day has passed since a full pass last listed the catalog, which the first pass after a restart always finds, and after a full pass that failed to write a column, which may have left that column on a copy a pass of changes would not list. With `download_images` off it removes the copies like any pass.
- **Failures.** An image the provider refuses (a 4xx response other than 429) or that is not a supported image is not requested again for a day. Downloads go one provider host at a time, each with its own count: transport failures, rate limits and server errors stop that provider's downloads for the pass after three in a row, and are retried on the next pass. Until its copy is saved, an image keeps its source: a TMDB path, or the Spotify or Apple URL of an album cover or musician photo. Shutdown cancels a pass; files it saved without pointing a column at them are removed by the next pass, which also skips removal whenever a write failed.
- **Safety.** Only files named as above and leftover `.tmp-*` files are removed, never `avatars/` or anything else. A managed folder that is, contains or lies inside a media library, the filesystem root included, is never written or pruned, with symlinks resolved on both sides first: a folder that links into a library is that library. Its columns go back to their sources. The check uses the library roots a pass started with; a pass whose roots change while it runs dispatches no more downloads and removes no further file or folder, even partway through a cleanup, and saving the library settings starts another pass, which checks the new roots. Turning the setting off counts as unfinished until a cleanup gets through with the same roots. A key folder is one the syncer creates, so one that is a symlink or not a directory is never written through, and a copy reached through it counts as missing. A full pass that finds every copy missing from the static directory the copies were made in, which the database records, and none of the managed folders they were in, skips itself with a warning, also on the first pass after a restart, since that is what a disk that has not mounted looks like; turning the setting off and on again downloads them again. A pass of changes, which sees only the copies in its folders, does not count them; it skips itself with the same warning when none of the managed folders that held copies after the last full pass, or were filled since, is there, symlinks followed. Copies deleted from a managed folder that is still there are downloaded again by the next full pass, even when they were all of them.
- **Turning it off**, or moving the static directory while it is on, points every column back at its source in one transaction before the settings save answers, so a client that refetches its library pages gets no URL of a copy about to be removed or left behind; the web client invalidates them on such a save, and the audio player replaces the covers of its queue, album by album, without stopping playback. A pass then deletes the copies and the folders left empty, or downloads the copies into the new directory and leaves the old one alone. Later passes repeat the removal until one gets through every folder without a filesystem error, then stop until the setting or the static directory changes.
- Logs report each pass that changed something (its `scope`, `full` or `changes`, and the downloaded, reused, failed, reverted and removed counts) and progress every ten seconds while downloading. There is no status endpoint.

## Sources and verification

The scanners share [fingerprint detection](../server/cmd/internal/scanner/fingerprint.go), [reconciliation](../server/cmd/internal/scanner/reconciliation.go), [move detection](../server/cmd/internal/scanner/moves.go), and the transaction runner. Provider persistence is covered by each scanner's enrichment, recovery, identity/merge, and cancellation tests. TV filename rules are covered in [parsing tests](../server/cmd/internal/scanner/show/parsing_test.go); file identity and safe deletion have dedicated fingerprint, moves, cleanup, and changes tests in all three scanners.

Watcher behavior is implemented and tested under [scanner/watch](../server/cmd/internal/scanner/watch). Artwork layout, provider URLs, scoped passes, settings races, mount/overlap checks, and cleanup are implemented and tested under [artwork](../server/cmd/internal/artwork), with source-column triggers in the [schema](../server/sqlc/schema.sql). Provider fixture tests do not verify live provider availability.
