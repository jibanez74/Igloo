Yes — **on Nvidia Shield / Android TV, MKV direct playback is realistic**, including through `expo-video`, **as long as the tracks inside the MKV are supported by the device/player**.

The key distinction is:

```text
MKV container support ≠ every codec inside the MKV is supported
```

Android’s platform media docs list **Matroska / `.mkv` support** going back to Android 4.0+, and ExoPlayer/Media3 also supports Matroska as a progressive container. ([Android Developers][1])

## What this means for `expo-video`

`expo-video` on Android uses the native Android media stack/ExoPlayer-style playback path. So on an Nvidia Shield, you should be able to direct play URLs like:

```tsx
const player = useVideoPlayer({
  uri: "http://your-server.local/api/videos/123/direct",
}, player => {
  player.play();
});
```

And that URL can point to an `.mkv` file, provided your Go backend serves it correctly with range requests.

## What will probably direct play well on Nvidia Shield

These are realistic direct-play candidates:

```text
MKV + H.264 + AAC
MKV + H.264 + AC-3
MKV + H.264 + E-AC-3
MKV + H.265/HEVC + AAC
MKV + H.265/HEVC + AC-3 / E-AC-3
MKV + VP9 + Opus
```

The Nvidia Shield is much stronger than a generic Android TV stick, so it can direct play many files that weaker devices cannot.

## What may still fail

These are the cases where `expo-video` may not be enough:

```text
MKV + DTS
MKV + DTS-HD MA
MKV + TrueHD
MKV + PGS subtitles
MKV + ASS/SSA subtitles
MKV + unusual HEVC profile/level
MKV + Dolby Vision profile not supported by the device/player path
```

The file may open, but you could get:

```text
video with no audio
audio with black screen
no subtitle rendering
track-selection issues
complete playback failure
```

Android/ExoPlayer support depends on device decoders and platform capabilities, not just the React Native package. Google’s ExoPlayer docs explicitly frame sample-format support around the Android platform’s available decoders. ([Android Developers][2])

## For Igloo, the direct-play rule should be track-based

Do not decide direct playback only by file extension.

Bad:

```ts
if (file.endsWith(".mkv")) {
  directPlay();
}
```

Better:

```ts
if (
  container === "mkv" &&
  videoCodecSupportedByClient(videoCodec) &&
  audioCodecSupportedByClient(audioCodec) &&
  subtitlesSupportedByClient(subtitleCodec)
) {
  directPlay();
} else if (
  containerNeedsChangeOnly ||
  audioNeedsTranscodeOnly ||
  subtitlesNeedExtraction
) {
  remuxOrAudioTranscode();
} else {
  fullTranscode();
}
```

For the Nvidia Shield client profile, you can be more permissive than for Apple TV or web.

## Recommended Nvidia Shield profile

For an Android TV / Nvidia Shield profile, I would model it roughly like this:

```ts
const nvidiaShieldProfile = {
  containers: ["mp4", "mkv", "webm", "ts"],
  videoCodecs: ["h264", "hevc", "vp8", "vp9", "av1"], // AV1 depends on Shield model
  audioCodecs: ["aac", "mp3", "ac3", "eac3", "opus", "vorbis", "flac"],
  unsafeAudioCodecs: ["dts", "dts_hd", "truehd"],
  subtitleCodecs: ["webvtt", "srt"],
  unsafeSubtitleCodecs: ["pgs", "ass", "ssa"],
};
```

For `dts`, `dts_hd`, and `truehd`, I would not assume reliable direct play through `expo-video`. You can test specific Shield behavior, but for a self-hosted media app you should keep a fallback path.

## Practical backend strategy

For Nvidia Shield:

```text
1. Try direct play for MKV when video/audio/subtitles are compatible.
2. If only audio is incompatible, keep the video and transcode audio to AAC or AC-3.
3. If subtitles are PGS/ASS and must be burned in, transcode video.
4. If the video codec/profile is unsupported, full transcode.
```

So the answer is: **yes, you can support MKV direct playback on Nvidia Shield with `expo-video`, but only for compatible track combinations.** It should be a client-profile decision, not a global rule.
