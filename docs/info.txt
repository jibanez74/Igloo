The biggest difference is this:

**`expo-video` is the Expo-native video API. `react-native-video` is the older, more customizable community player.** Both rely on native players underneath, so codec support is mostly the same class of problem: ExoPlayer/Media3 on Android and AVPlayer on iOS/tvOS.

## Core comparison

| Area                | `expo-video`                                                                                              | `react-native-video`                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Best fit            | Expo apps, especially Expo Router / Expo TV projects                                                      | Bare React Native or Expo projects that need deeper player control                                    |
| Underlying player   | Native platform player through Expo module                                                                | ExoPlayer on Android, AVPlayer on iOS/tvOS, HTML5 on web                                              |
| TV compatibility    | Official Expo docs list Android, iOS, tvOS, and Web support for `expo-video`                              | v6 docs mention AVPlayer for iOS/tvOS, but current v7 repo marks TV support as TODO/in progress       |
| Setup               | Easier in Expo; `npx expo install expo-video`                                                             | More native setup; has Expo plugin support but is still more custom                                   |
| API style           | Modern hook-based API: `useVideoPlayer`, `VideoView`, player events                                       | Traditional `<Video>` component in v6; v7 introduces newer API but is still active development        |
| Track control       | Supports available audio/subtitle track events and track selection APIs, but the API is more Expo-managed | Usually exposes more low-level control for buffering, events, tracks, DRM, ads, and playback behavior |
| DRM                 | Supports DRM configuration, but less battle-tested for complex OTT needs                                  | Stronger history around Widevine/FairPlay and production streaming use cases                          |
| Offline / downloads | Has caching support on Android/iOS, with limitations                                                      | Offline/download support often involves extra/commercial SDK pieces                                   |
| Maintenance path    | Maintained by Expo, aligned with Expo SDK releases                                                        | Maintained by TheWidlarzGroup/community; v6 stable, v7 active development                             |

Expo’s TV guide says Expo apps can target Android TV and Apple TV by using the `react-native-tvos` package, and the `expo-video` docs list Android, iOS, tvOS, and Web support. ([Expo Documentation][1]) `react-native-video` v6 describes itself as using ExoPlayer on Android and AVPlayer on iOS/tvOS, with features like subtitles, DRM, PiP, and embedded controls. ([docs.thewidlarzgroup.com][2])

## For your media-center use case

For **Igloo**, I would think about it this way:

### Use `expo-video` if you want the cleaner Expo path

Choose `expo-video` if your TV client is going to stay close to the Expo ecosystem:

```ts
import { useVideoPlayer, VideoView } from "expo-video";
```

It is probably the better default if you are using:

```text
Expo
Expo Router
react-native-tvos
Android TV + Apple TV targets
simple custom controls
HLS/MP4 playback
server-side compatibility decisions
```

This fits your architecture well because your Go backend already handles media analysis, transcoding, remuxing, and streaming decisions. In that setup, the client does not need to be a powerful universal decoder. It needs to be a reliable native player for compatible streams.

### Use `react-native-video` if you need deeper playback control

Choose `react-native-video` if you need more direct control over things like:

```text
buffer configuration
DRM edge cases
custom track selection
low-level player events
analytics / QoE reporting
advanced HLS/DASH behavior
more mature production streaming examples
```

The package has a longer history in React Native streaming apps and explicitly advertises HLS, DASH, SmoothStreaming, DRM, offline playback, and advanced playback control. ([GitHub][3])

The caution is that `react-native-video` is in a transition period: v6 is maintained, while v7 is active development and the repo warns that v7 can have breaking changes and missing features. ([GitHub][3]) For TV specifically, I would test carefully before committing.

## Code style difference

With `expo-video`, the mental model is:

```tsx
const player = useVideoPlayer(source, player => {
  player.play();
});

return <VideoView player={player} />;
```

With `react-native-video` v6, the model is more like:

```tsx
<Video
  source={{ uri }}
  onBuffer={handleBuffer}
  onError={handleError}
  controls
/>
```

So `expo-video` feels more like a modern Expo module with a player object. `react-native-video` feels more like a classic React Native component with many props and callbacks.

## My recommendation for you

For your current direction, I would start with **`expo-video`** unless you hit a specific limitation.

Reason: your project is self-hosted, your backend already controls the media pipeline, and you care about Android TV/tvOS compatibility. The cleaner strategy is:

```text
Client:
expo-video + custom TV-friendly controls

Backend:
decide direct play vs remux vs transcode

Preferred stream output:
HLS or MP4
H.264 / HEVC where supported
AAC stereo
optional AC-3 / E-AC-3 surround
WebVTT subtitles
```

Move to `react-native-video` only if `expo-video` blocks you on a concrete requirement, such as track selection behavior, buffering controls, DRM, subtitle rendering, or specific TV remote-control/player-control integration.
